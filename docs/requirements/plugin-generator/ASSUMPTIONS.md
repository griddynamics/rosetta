# plugin-generator — Assumptions, Quirks, Open Questions

## Assumptions (AC)

- **AC-1 — Uniform generation is the intent; two-pass derivation was an accident (now codified).** The old Python generator generated the four "main" targets first, then derived the two standalone targets by reading from the already-generated main plugin trees. Per the maintainer, this coupling caused repeated defects and is *not* a requirement. Target state — now a requirement, not just an assumption: all targets are generated independently from the instruction source by the same pipeline (FR-CLI-0040; standalones explicitly uniform-from-source in FR-VAR-0050/0051). Requirements capture per-variant **output properties**, never the derive-from-main mechanism. This also retires the `.cursor/.cursor/` self-nesting guard (QF-4).
- **AC-2 — Parity bar is per-target structural, not byte-for-byte (SUPERSEDED).** The former byte-for-byte-vs-old-generator bar is retired: the Python generator (the byte-identity reference) was removed, so a content-diff oracle can no longer run. Parity is now per-target **structural** — the generated output file-path set must equal the set derived from the instruction source and that target's mapping contract (NFR-0001); content is not compared. Declared-new behavior (e.g. `--domain`, dry-run) has no baseline and is excluded.
- **AC-3 — Hook bundles are an external input.** `src/hooks/dist/bundles/<target>` and `src/hooks/dist/shell/` are produced by a separate build step. The generator assumes they exist when a release requires deterministic hooks. This covers only the compiled `*.js` runtime bundles, not the preserved manifests/templates (see AC-3a).
- **AC-3a — Preserved manifests and templates are a committed source, not an output-tree precondition (RESOLVED).** Earlier behavior depended on each target's IDE manifest (`plugin.json`), hook templates (`*.tmpl`), config-folder contents, and any `.mcp.json` already existing inside the committed output tree (`plugins/<target>/...`), surviving the wipe as preserved paths — so generating into a clean/empty output directory required manually seeding them (observed in discovery §7 and the validation report). Resolved: these preserved files now have a committed source under `src/rosettify-plugins/plugins/<template>-<ide>/` (DATA-CFG-0005) that `pluginCopy()` copies into the output before generation (FR-SEED-0001, FR-ARCH-0053). Since ticket #315 the folder is a shared template rather than a per-plugin copy, so several sets seed from one folder and standalone targets seed from their parent IDE's template (FR-SEED-0002). There is no longer any "survive the wipe" semantics: `pluginCleanup()` empties the output and `pluginCopy()` re-establishes the preserved files from source every run.
- **AC-4 — Instruction source layout is stable (AMENDED #315).** Source content lives under typed folders (`agents/`, `rules/`, `skills/`, `workflows/`), now nested one level deeper: `instructions/<release>/<set-folder>/<typed-folder>/`, where `<set-folder>` is one of `core`, `workflows`, `qe`, `search`, `modernization` for `r3` and `core` alone for `r2`. Agent files are `agents/<name>.md` exactly one level deep within their set folder. There is no `configure/` folder — the per-IDE guides are reference material of the `harness` skill — and `templates/` belongs to no plugin set and ships nowhere.
- **AC-5 — Run via npx.** The re-implementation targets a TypeScript/Node runtime invoked through `npx`, replacing the Python entry point; the Handlebars dialect and filesystem operations have direct Node equivalents.
- **AC-6 — Logical model keys are release-neutral.** Frontmatter `model:` values are logical keys (`opus`, `sonnet`, `gpt-5.4`, …); the per-IDE version strings they map to are config expected to change.

- **AC-14 — Copilot produces three distinct hooks.json files (CONFIRMED INTENDED).** The `copilot` target emits `hooks.json` (root), `.github/plugin/hooks.json`, and `hooks/hooks.json` — three separate files at three distinct paths. The root and `.github/plugin/` copies are byte-identical (alternate-name duplication, FR-VAR-0031, FR-COPY-0033); `hooks/hooks.json` is the standalone-form rendered output with distinct content (`"sessionStart": []`). This is confirmed by MD5 comparison in r2/r3 baselines and is codified in FR-VAR-0030/0031 and STRUCTURES.md. The original STRUCTURES.md diagram omitted `hooks/hooks.json` and mischaracterized the root copy as a `fileRename()`.

## Flagged Quirks / Findings (QF) — current behavior, not necessarily intended

- **QF-1 — Order-sensitive bootstrap prefix (RESOLVED, then prefix REMOVED 2026-07-28).** The bootstrap prefix attached to the *first bootstrap-classified file found* per target; reordering the bootstrap file list silently moved the prefix. Resolved in the target state: the bootstrap-file order became an explicit, required, deterministic manifest (FR-HOOK-0009) and the prefixed document an explicitly designated lead — not position-dependent. The quirk is now **moot**: the prefix was removed entirely on 2026-07-28 (FR-HOOK-0003 Deprecated) because session-start hooks are small and `get_context_instructions` is no longer used in this flow. With nothing to place, the lead designation was removed too — no entry is treated differently by position, and the leading-newline strip applies uniformly to every entry. Note: bootstrap-file order remains **significant** (it fixes payload entry sequence); it is contractual rather than accidental.
- **QF-2 — Oversize payloads are a soft error (CONFIRMED INTENDED).** A bootstrap context entry exceeding 10000 characters is reported, still emitted, and sets a non-zero exit status. This soft-error behavior is intended (not a defect): the run completes so all problems surface together, and the non-zero exit signals the violation. Codified in NFR-0004.
- **QF-3 — Copilot duplicate-hook lock (RESOLVED — guard removed).** Copilot CLI used to invoke a single registered hook twice per real event; per-entry file locks were generated as a workaround. GitHub has since fixed the underlying defect (one registration now yields exactly one invocation), so the workaround no longer applies — Copilot delivers bootstrap the same way Claude/Codex/Cursor do, no per-entry guard needed.
- **QF-4 — Standalone subfolder self-nesting guard (RESOLVED).** When a source folder name equals the standalone's target subfolder (e.g. `.cursor`), special-case merging was needed to avoid `.cursor/.cursor/`. This was a defensive patch arising from the derive-from-main approach (AC-1). Resolved: a uniform generator writing directly to the target layout from the instruction source never produces the nesting (FR-VAR-0050), so the guard is unneeded.
- **QF-5 — Silent skips (RESOLVED).** Missing bootstrap-file variants and missing templates were skipped silently or with only a stderr warning. Resolved: every skip is logged — absent bootstrap variants (FR-HOOK-0001), missing templates (FR-GEN-0010), and per-processor decisions (FR-ARCH-0050).
- **QF-6 — Mixed concerns in one module (RESOLVED in target state).** Filesystem mechanics, IDE-specific string escaping (bash/PowerShell/TOML/JSON), model maps, and orchestration live in one file, and `copy_core_tree` fuses path renaming with content rewriting. This is the "awful architecture" the maintainer wants split. Resolved by the unified processor model: single-responsibility processors (NFR-0007, FR-ARCH catalog), with `fileRename()` path-only and `pluginRewriteReferences()` content-only.
- **QF-7 — Shallow regex corrupted prose (RESOLVED, regression lesson).** A prior re-implementation attempt rewrote the bare token `agents`→`.codex/agents` with an unanchored/substring match, corrupting the ordinary word "agents" throughout every document — even though that responsibility was paths only. Resolved and generalized: **every** regular expression and match in the generator must be strict and anchored/bounded — never shallow substring or bare-word — and reference rewriting consumes concrete resolved path pairs at token boundaries, not loose regex (FR-ARCH-0037, FR-ARCH-0049). The same lesson fixes the tag-membership substring risk (FR-GEN-0003).

## Target-state assumptions (added from rewrite design)

- **AC-7 — Unified architecture: FR-ARCH is normative; as-is FRs recast in place.** `FR-ARCH.md` defines the single target architecture — an immutable VFS (with structural sharing) and a **two-tier** pure single-responsibility processor pipeline (`FileProcessor` over a `FileProcessingFrame`, `PluginProcessor` over a `PluginProcessingFrame`). The reverse-engineered behavior FRs (`FR-COPY`, `FR-GEN`, `FR-HOOK`, `FR-VAR`) have been **recast in place** onto this model — not dropped: each now states its behavior as a `FileProcessor`/`PluginProcessor`/`SpecEntry` (e.g. rename→`fileRename()` path-only, content rewrite→`pluginRewriteReferences()`, reset→`pluginCleanup()`, seed→`pluginCopy()`, folder move→`SpecEntry` `target`, pre-copy→`SpecEntry`, inject→`pluginEmitDistributionRoot()`). The `npx -y rosettify-plugins@latest` implementation (`src/rosettify-plugins/`) is the parity target (NFR-0001). There is no longer a competing as-is procedural architecture in the requirement set.
- **AC-8 — Override is a directive, not deferred.** The `overwrite` filename directive provides per-file override now, realized by `fileApplyOverrides()`. The earlier "bundle, don't override" framing is replaced by the processor model: default behavior is `fileBundle()` concatenation; `overwrite` prunes earlier entries via `fileApplyOverrides()`.
- **AC-10 — Path and content are two responsibilities.** `fileRename()` changes only the target path; `pluginRewriteReferences()` changes only content. They are never fused (unlike the original `copy_core_tree`). This is the maintainer's explicit requirement and the headline of the unification (FR-ARCH-0043/0049, FR-COPY-0032).
- **AC-11 — Every step is a processor at its tier; no out-of-band passes.** `reset`→`pluginCleanup()` and seeding→`pluginCopy()` (head `PluginProcessor`s); a folder move→`SpecEntry` `target`; `pre_copy_folders`→additional `SpecEntry`; `pre_move_files`→relocation `SpecEntry`/`fileRename()`; `pre_cleanup`/`post_cleanup`→not emitting (`target_contents=null`). Every step is a `FileProcessor` or `PluginProcessor` in a declared pipeline (FR-ARCH-0035).
- **AC-12 — Exact matching is generator-wide; references are observed not recomputed.** Every regular expression and match is anchored and boundary-delimited to the complete token (FR-ARCH-0037). `pluginRewriteReferences()` builds its lookup by reading the per-file `frames` (source VFS path → final target path) plus the `SpecEntry` folder pairs — the renames are observed from the frames, never re-derived from the rename rules (FR-ARCH-0049).
- **AC-13 — Generated content is built against final paths.** `pluginGenerateIndexes()`/`pluginEmitDistributionRoot()` and any derived artifact are produced from post-`fileRename()` paths (FR-ARCH-0038), so generated content needs no reference rewriting; `pluginRewriteReferences()` touches only hand-authored body references. This minimizes both the work and the blast radius of reference rewriting.
- **AC-9 — RESOLVED. Directive delimiters are tilde fences with tilde separators (`name~token[~token...]~.ext`).** Brackets `[ ]` were rejected: they are **git-pathspec magic** (`git add 'foo.[1a].md'` matches a glob, not the literal file), glob character-class metacharacters, and regex character-class openers. The chosen delimiter — `~`, used as both fence and separator — is a valid filename character on NTFS/APFS/ext4, **literal in git pathspecs**, **not** glob/extglob metacharacters (so they are safe both as data matched by patterns and unmatched as patterns), and inert in regex; `~` does not trigger shell tilde-expansion mid-filename (it is not at word start). The directive segment is also stripped at VFS-build (FR-ARCH-0020), so it never reaches a rename/reference regex. Grammar stated in FR-ARCH-0020/0021 and GLOSSARY. (`( )` were considered and are git/OS/glob-safe but carry shell-quoting and regex-escape caveats, so the fully-inert tilde set was preferred.) An earlier revision of this entry described a comma separator between tokens; that notation was a documentation artifact and was never implemented — `parseDirectives` has always split the stem on `~` alone. The separator is a tilde; the closing fence contributes no token (AC-19). Since ticket #315 every selector token additionally carries a namespace prefix — `target-`, `ide-`, `set-`, `profile-` — which changes what a token means but not the delimiter reasoning above. The delimiter-safety reasoning above is unaffected, since `~` was always the fence character.

## Profile assumptions (added from profiles design)

- **AC-15 — `--profileSource` and `--config` default paths (CONFIRMED).** When `--profileSource` is omitted, the profile source directory defaults to `<source>/src/rosettify-plugins/profiles`, resolved off `<source>` exactly as `--pluginsSource` resolves its own default; a named profile is loaded from `<profileSource>/<name>.json`. The same resolution rule governs `--config`, whose default is `<source>/src/rosettify-plugins/plugins.json` (FR-CLI-0034). Both defaults confirmed by the owner on 2026-09-01.
- **AC-16 — Filtered model-list survivor order is SOURCE order; de-duplication keeps the FIRST occurrence.** When a comma-list of models (e.g. `subagent_required_model`) is filtered through the effective model vocabulary, the surviving entries keep the order they held in the source list, and any duplicate produced by mapping is removed by keeping the first occurrence.
- **AC-17 — A dead inner override entry is ignored silently.** An inner `modelOverrides` entry whose key matches no model token anywhere in the instruction source has no effect: no warning, no failure. (This is validation rule V5 of the profile descriptor.)
- **AC-18 — Standalone targets inherit their parent's override block; an explicit block overrides.** A standalone target that declares no `modelOverrides` block inherits its parent's block (`cursor-standalone` ← `cursor`, `copilot-standalone` ← `copilot`). An explicit standalone block overrides the inherited one. Preserved files for standalones still derive from the parent IDE's template folder (FR-SEED-0002).
- **AC-19 — The closing tilde fence of a `FilenameDirective` contributes no token.** The closing `~` fence produces an empty trailing segment. This entry anticipated that a future known-token allow-list would have to account for it, and that validation now exists (FR-ARCH-0060): `parseDirectives` drops the trailing empty segment before checking each token against the allow-list, so the fenced form validates and no empty string reaches the check. The prediction held — a naive allow-list would have rejected every fenced filename in the instruction set. The allow-list has since gained the `target-`, `ide-` and `set-` namespaces (#315); the empty-trailing-segment handling is unaffected.
- **AC-20 — AC-6 extends to profile-scoped map substitution.** AC-6 (logical model keys are release-neutral) also holds when a profile substitutes a target's model map: the logical keys stay release-neutral and the profile's per-target block supplies the IDE-specific values in place of the built-in map. The block is keyed by the bare IDE identity (`claude`, `cursor`, …) since #315.
- **AC-21 — A profile affects only its own variant (AMENDED #315).** A profile changes only the output of the variants that name it; a variant naming no profile produces exactly what it produced before profiles existed. Since one run now builds profiled and unprofiled variants side by side, this guard is stated per variant rather than per run (FR-PROF-0040).

- **AC-22 — A set-only token's id is validated by shape, not resolved.** `set-<id>-only` requires a non-empty id and is never checked against the declared sets, mirroring `profile-<name>-only` (FR-ARCH-0025, FR-ARCH-0060). Resolving it would make VFS parsing depend on the plugin-set configuration and would break a legitimate `--domain`-filtered run that builds none of the sets a file names. Consequence accepted: a typo such as `set-qee-only` parses and silently matches nothing.
- **AC-23 — Sets are disjoint; layering is a mechanism, not a merge in practice.** Every file under `instructions/r3/` belongs to exactly one set folder, so the combo set's layering performs no bundling today (FR-SET-0020.AC5). The layering mechanism is nonetheless specified in full, because the combo `rosetta` set declares five folders and relies on it, and because any future set declaring more than one folder will too. Whether the folders stay disjoint is enforced outside the generator.
- **AC-24 — `requires` is unenforceable and stated as documentation.** No IDE the generator targets has a plugin dependency mechanism, so a domain plugin installed without `core` and `workflows` fails at use time by failing to resolve a skill or subagent name, not at install time. The generator's only action is to surface the list in the manifest description (FR-SET-0050); mixing the combo distribution with the split distribution is likewise unenforced.

## Open Questions (OQ)

- **OQ-1 — RESOLVED.** Bundling is plain concatenation by `fileBundle()` with no markup/delimiters, in VFS order (set by order tokens / filename sort). No `<rosetta:file>`-style tags (unlike the server Bundler). See FR-ARCH-0042.
- **OQ-2 — RESOLVED.** Per-file override exists now via the `overwrite` directive (AC-8, FR-ARCH-0024/0041).
- **OQ-3 — RESOLVED.** Model normalization applies uniformly to all domains. Omission ("do not ship in any plugin") is a `SpecEntry.exclude` field — an array of VFS paths the entry must not emit (FR-ARCH-0002/0054, FR-COPY-0011). The legacy `rules/bootstrap.md` and `rules/local-files-mode.md` are listed there. This composes with a set's declared folders (each entry owns its omissions), `--domain` being a filter over sets rather than an overlay axis, and requires **no** source rename or directive — the source files stay unchanged because MCP serves them and instructions reference them.
- **OQ-4 — RESOLVED (subsumed).** The parity bar is per-target structural everywhere, not byte-for-byte (NFR-0001, AC-2): output file-path sets must equal the derived-expected set; content is not compared. Hook JSON is covered by this general structural rule like any other output.
- **OQ-5 — RESOLVED.** The VFS is built from structure + filename directives only (FR-ARCH-0011); each file's `frontmatter` slot is populated by `fileRead()` during processing (FR-ARCH-0040), not at VFS-build time, consistent with content I/O being confined to `fileRead`/`pluginWrite` (FR-ARCH-0033). The post-`fileRead()` working state carries the populated frontmatter.
- **OQ-6 — RESOLVED (#315).** Multi-folder bundling order is the set's declared `folders` array and no longer depends on command-line argument order (FR-SET-0020, FR-CLI-0031). Alignment with the server Bundler's `sort_order` is moot for `r3` as it stands: the five set folders are disjoint, so no two contribute a file at the same VFS path and no bundling occurs across them (FR-SET-0020.AC5). Should a future configuration declare overlapping folders, the declared order governs. Previously mislabelled `OQ-1`, which collides with the RESOLVED OQ-1 above; renumbered here.
- **OQ-7 — OPEN. Is `set-<id>-only` needed by any instruction file today?** `FR-ARCH-0025` specifies the token because plugin identity became two-dimensional, but no source file carries it, exactly as no target-only or IDE-only token is carried today. If the split holds without one, the kind is specified-and-unused — acceptable, since specifying it is what makes the four namespaces symmetric and an unrecognized token a hard failure (FR-ARCH-0060).

## `codex` target — facts and decisions

- **CX-1 — Workflows are skills.** For the `codex` target, the generator packages workflows under the existing manifest-declared `.agents/skills/` skills root and emits no `.agents/workflows/` folder (FR-VAR-0042).
- **CX-2 — No index at all (AMENDED #315).** For the `codex` target, the generator now generates no folder index of any kind — the rules index went with the workflows index — and its session-start hook payload carries no index entry (FR-VAR-0041, FR-HOOK-0004, FR-GEN-0001 dormant).
- **CX-3 — Target-specific behavior stays isolated.** For the `codex` target, the generator retains Codex model normalization and does not apply the `antigravity` frontmatter reduction or subagent-model rewriting (FR-VAR-0042). The advisory-hook exclusion is no longer a target-specific behavior at all: it is an instance of a set's declared hook list (FR-VAR-0083, FR-SET-0070).

## Antigravity — facts and decisions

Antigravity mirrors the Claude plugin package pattern except the exceptions below. Authoritative hooks reference: `docs/hooks/antigravity.md`; the hook contract is identical across all three products.

- **AG-1 — Hooks.** `SessionStart` is not an event (its analog is `PreInvocation @ invocationNum:0`); `PostToolUse` output is ignored — so the advisory hooks `lint-format`/`md-file`/`loose-files` are excluded, expressed since #315 as a hook list a set declares rather than a target-named rule (FR-VAR-0083, FR-SET-0070); bootstrap rides the always-on rule; `PreInvocation` is reserved for other hooks.
- **AG-2 — No model emitted.** Agent and skill frontmatter is reduced to `name`+`description` (FR-COPY-0081); `subagent_required_model`→`inherit` (FR-COPY-0082); no model vocabulary. Antigravity maps its selectable tiers (flash_lite/flash/pro) to old models, so specifying one is worse than none — the runtime selects its own current model.
- **AG-3 — `trigger: always_on`** is honoured across all three products. The always-on rules live in the `core` folder, so an Antigravity plugin bootstraps only where the building set includes it (FR-SET-0070).
- **AG-4 — Rule activation is author-controlled.** The generator never sets or adds `trigger:`; source rules carry their authored activation (`bootstrap-alwayson.md`/`plugin-files-mode.md` = `always_on`; `speckit-integration-policy.md` = `model_decision`; `coding-iac-best-practices.md` = none). Rule frontmatter is copied unchanged (FR-VAR-0081). All five rules live in the `core` folder.
- **AG-5 — Indexes (SUPERSEDED #315).** Folder indexes were generated as for Claude (a rules index and a skills index). No plugin set declares an index now, so the Antigravity plugin carries none (FR-VAR-0080, FR-GEN-0001 dormant).
- **AG-6 — IDE guides verbatim (RESTATED #315).** There is no `configure/` folder any more; the per-IDE guides are reference material of the `harness` skill at `skills/harness/references/configure/`. They still belong in the package for the same reason — an Antigravity install can itself author content for Claude Code or any other tool — and they still require verbatim treatment, since each documents another IDE's on-disk layout that reference rewriting would corrupt (FR-ARCH-0049).
- **AG-7 — workflows→skills.** The Antigravity CLI has no workflows; for the `antigravity` target, the generator packages workflows as skills through the shared transform (FR-COPY-0080).
- **AG-8 — Phase files are body-only.** For the `antigravity` and `codex` targets, the generator emits workflow phases without YAML frontmatter (FR-COPY-0080).
- **AG-9 — One Antigravity target, many sets.** The single `antigravity` IDE target is built once per declared set variant, so an install may hold `rosetta-antigravity` or `core-antigravity` + `workflows-antigravity` + domain plugins, never both distributions (FR-SET-0060). Antigravity enforces no plugin dependency, so a `requires` list is documentation only (FR-SET-0050).
