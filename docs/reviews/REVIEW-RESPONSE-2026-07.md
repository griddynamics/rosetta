## V · The Findings

| ID | Locator | Type | Disposition | Architect response |

| R-044 | Finding 01 — untrusted prompt review runs with a secret and a shell | Claim | Partially Accepted | Two of three mechanics are wrong. No untrusted code executes anywhere in this job. Root checkout is `ref: main`, the system prompt is read from main, the plugin installs from the published marketplace. Fork content lands in `pr/` and is read as data. So there is no pwn request - there is one attack class here, not two. Second, it is not an Anthropic key. It is a Bifrost gateway key with ANTHROPIC_BASE_URL overridden to our gateway. Gateway scoped, revocable, spend capped. Injection on the diff is real. Prompt level guardrails are our control class by design, same as everywhere else in Rosetta, and the tool scope is being tightened on top of that - `Bash` in this job is being narrowed to read-only `git *`, which is all the auditor needs to fetch base versions of changed files. That removes the exfiltration primitive without touching the trigger. Reviewer read the trigger and the env block and stopped. It never opened the system prompt, so it could not assess the control that is there. |
| R-045 | Finding 01 remedy — split into two stages | Proposal | Rejected | Sanitised diff does not work for this payload class. The payload IS instruction shaped markdown, because that is the artifact under review. Sanitisation cannot neutralise semantic text. And removing shell and egress removes the review itself - the auditor needs git to fetch base versions of changed files and Task to split large diffs across subagents. This is a workflow rewrite prescribed without reading what the workflow does. The proportionate fix is narrowing the tool scope - read-only `git *` instead of full `Bash` - which kills the same primitive at a fraction of the cost. |
| R-046 | Finding 02 — guardrails not authoritative by default | Claim | Already Addressed | Defaults off is release strategy, see R-002, and it is a fixed requirement in the generator, not an accident. Two specifics are simply wrong. The matcher is `Bash|Write|Edit|MultiEdit|mcp__.*` when hooks are on, and evalWrite, evalEdit and evalMultiEdit are all implemented against dangerous paths and dangerous content - writes and edits are covered, not excluded. And the marker is not a free pass: it is honored only in user visible write time fields - command, content, new_string, edits - never in file_path or old_string so it cannot retarget the operation, and never in hidden fields like description so the model cannot assert it quietly. Two tiers only: advise never blocks, reconsider soft denies. Approval is not the hook's job anyway - the dangerous-actions skill and hitl rule 16 mandate explicit user approval in every host, hooks or no hooks. The hook is the accident net, not the gate. Reviewer never opened the hook source or the prompts. |
| R-047 | Finding 02 remedy — ship enforcement on, signed token | Proposal | Rejected | Three parts, three problems. Ship on - release strategy, R-002. Match every side effecting class - it already does, the matcher is `Bash|Write|Edit|MultiEdit|mcp__.*`. Signed token the model cannot mint - this breaks the product. The patterns are `rm -rf`, `git reset --hard`, `git clean -fd`, `DROP TABLE`, `curl \| sh`. On a laptop, a scratch branch or a dev container those are normal work. An unmintable token means a human in the loop every single time in throwaway environments. We chose reconsider deliberately: stop the accident, force a visible re-declaration in the field the user actually sees, keep the legitimate path open. The hard gate lives in the skill and in hitl, not in a token. |
| R-048 | Finding 03 — context management progressive but not model-aware | Claim | Partially Accepted | Four sub-claims, one fair, three wrong. Document count threshold - true, and it is not a token budget, it is a fan-out guard: 5 or fewer returns bundled content, more returns a listing so the agent pulls specific files by tag. Instruction files are size-capped by schema and compression rules, so count is a workable proxy. No per-model capability record - that is deliberate and dated. Context thresholds are percentages ONLY, absolute token counts were removed on 2026-07-11 because models now reach 1M. Percentages are model agnostic by construction; a capability registry is exactly what they make unnecessary. The host reports percent used, we react to percent. Startup injection - measured 9,139 bytes of JSON-escaped hook file, and it is not "commands": it is `bootstrap-alwayson` core policies plus the rules and workflows indexes. That is the always-on layer, the product itself, and about 2K tokens for it is the compression result, not overhead - everything else loads on demand. And the remedy is not "tell the user to start a new session": `self-organization` is a proactive scope skill - plan as todo tasks, reduce scope past 2h or 15+ files or 350+ lines, about 2 pages per review pass, batch writes on overflow, warn at 65% and escalate at 75%. The agent emits that, not an engineer watching a gauge. |
| R-049 | Finding 03 remedy — move budgeting into the harness | Proposal | Rejected | It is already in the harness - the harness owns the model and the window, which is the R-091 boundary the reviewer itself states.
