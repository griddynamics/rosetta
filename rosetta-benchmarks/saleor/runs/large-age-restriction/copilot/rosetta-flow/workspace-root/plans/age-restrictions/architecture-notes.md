# Age restrictions — architecture notes

**Status:** Draft for coding-flow phase 3 design review; not approved for implementation.  
**Scope:** Saleor backend, Saleor Dashboard, Paper storefront. Local source inspection only, 2026-11-08.  
**Decision:** Recommend a shared backend domain policy with explicit protected-operation adapters. Clients provide notices and recovery, never eligibility authority.

## Summary

Add a Product Boolean flag, database-backed shop minimum age/time zone, and nullable customer birthday. The new validated IANA `timeZone` field in `shopSettingsUpdate` defaults to UTC and is shown in Dashboard Site Settings only, not Paper. It determines shop-local `today`; eligibility compares dates, qualifies on the threshold birthday occurring today, and treats 29 February birthdays as 1 March in non-leap years.

Existing guest checkouts retain restricted lines without pruning: guest additions and non-removal quantity updates/increases are blocked, removal remains allowed, and completion is blocked with an error naming the restricted product. Guest browsing remains allowed; Paper prompts sign-in. Completion rechecks authoritatively using current policy. Existing placed orders remain unchanged.

The important seams extend beyond `checkoutLinesAdd`, `checkoutLinesUpdate` and `checkoutComplete`: checkout creation with lines, reorder checkout creation, app-only `orderCreateFromCheckout`, legacy payment completion, automatic completion, draft creation/edit/completion and replacement drafts. An API-only implementation limited to the three named mutations would leave alternate entry paths.

Birthday requires explicit actor-and-object authorization. Existing `MANAGE_USERS` permissions and account impersonation are **not** authority to read or write birthdays. Paper currently discards cart mutation errors; surfacing failures is part of this feature, not an optional polish task.

## Three alternatives — design analysis, not existing-code facts

Scoring: 1 poor, 5 strong. Weighted result uses policy integrity 35%, security/privacy 25%, compatibility 15%, maintainability 15%, testability 10%. Weights are this review's commerce-risk rubric, not a user requirement. All alternatives keep the confirmed first-class database fields; metadata/per-product numeric rules/external age services are not eligible alternatives.

| Option | Policy integrity | Security/privacy | Compatibility | Maintainability | Testability | Weighted /5 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A — Inline validators per mutation/task/order path | 3 | 3 | 4 | 2 | 3 | 3.00 |
| **B — Shared domain evaluator + explicit operation adapters** | **5** | **5** | **4** | **5** | **5** | **4.85** |
| C — Model save/signal enforcement with operation-context bypasses | 3 | 3 | 2 | 2 | 2 | 2.60 |

### A — Distributed inline validation

**Shape:** Each checkout/draft/reissue mutation or action owns its validation, date calculation and error mapping.

**Pros:** Small local patches; easy initial mutation tests; no new domain module or broad low-level interface.

**Cons/consequences:** Leap-day/time-zone and actor rules repeated across legacy/modern/background paths; new route must remember every rule. GraphQL guard does not cover direct domain calls. Correct lock-time delta classification still requires deeper adapters. App impersonation and webhook privacy drift independently.

**Strongest case:** Narrow, single-client feature with few entry points. **Why rejected here:** B19–B32 establish many independent creation paths; duplication is the primary bypass/drift risk.

### B — Shared domain policy with explicit adapters — recommended

**Shape:** A small pure evaluator plus backend loading/authorization helpers, reused by checkout/draft/reissue protected-operation adapters. GraphQL owns input validation and error projection; domain adapters own transactional enforcement. UI consumes public policy and self-only profile state.

**Pros:** One date rule, one birthday authorization rule, deterministic testing; completion and indirect routes use the same policy; exceptions remain explicit. Existing API shapes, commerce locks and partial-update conventions remain.

**Cons/consequences:** Must inventory/wire every protected route; extra writer reads for fresh policy/customer/product state; birthday inputs shared by inheritance need carefully guarded handling. Older clients cannot create restricted orders until they support the new profile requirement.

**Failure mode/control:** An omitted adapter becomes a bypass; route-matrix regression tests and shared checkout-line write enforcement defend against it. The helper is not automatically invoked by arbitrary ORM writes, which remain outside the public API/domain-operation contract.

### C — Model save or signal policy

**Shape:** Enforce around User/CheckoutLine/Order/OrderLine saves/signals, using request/operation context to distinguish drafts, imports, decreases and privileged birthday edits.

**Pros:** Broad apparent coverage; rules near stored state; can intercept some direct ORM writes.

**Cons/consequences:** Aggregate lines may not exist when Order is first saved; bulk operations bypass ordinary save/signals. No reliable actor at generic model save; background tasks lack request context. Explicit `orderBulkCreate` exemption and unchanged historical orders require bypass/context flags. Signals risk rejecting ordinary unrelated saves or failing after payment/events.

**Strongest case:** Simple single-row invariant with no actor/aggregate exceptions. **Why rejected:** This policy is actor-, operation- and aggregate-dependent; B18, B24 and B31–B32 show why a generic save hook is the wrong boundary.

## Recommended architecture — proposed target, pending review

### Data and API ownership (R1–R3, R8)

- Product stores `is_age_restricted`, default/db default false. GraphQL adds public `isAgeRestricted: Boolean!` and optional input field to ProductInput; omission preserves old-client behavior, explicit false clears it. ProductCreateInput/bulk creation inherit it; verify construction/tracking rather than relying on schema inheritance alone.
- SiteSettings stores `minimum_age` (18) and proposed database field `time_zone` (UTC), including database defaults. **Confirmed API name:** new `ShopSettingsInput.timeZone` in `shopSettingsUpdate`, validated as an IANA zone; expose `Shop.timeZone` for the Dashboard settings read/response through the existing Shop projection. ShopSettingsUpdate retains `MANAGE_SETTINGS`. Dashboard Site Settings displays/edits the zone; **Paper neither selects nor displays `timeZone` and has no zone editor**. Public minimum-age notices do not require sending the zone to Paper. Database field naming remains a proposed implementation detail; `timeZone` is no longer a proposed API alias. Trace: R2 → B2/B8/B9 → D5/D6/D8.
- Validate integer minimum and time-zone membership/resolution with Python's IANA zoneinfo support; reject malformed/non-IANA strings and explicit nulls for nonnullable settings. Do not silently normalize an invalid zone to UTC. No arbitrary regulatory upper age or jurisdiction rule is introduced; precise numeric range/error contract belongs in the reviewed spec.
- User stores nullable date-only `birthday`; existing users remain null. No birthday inference from account creation date, customer attributes, metadata, addresses or imported orders.
- Add three additive schema migrations in account/product/site following their current migration leaves. Defaults must protect old-code inserts during rollout. No data migration changes existing cart/order rows; no chosen migration numbers before implementation.
- Use existing AccountInput/accountUpdate for self profile edits and CustomerInput/customer mutations for superuser access. Apply a shared birthday-specific actor/object guard across inherited create/update inputs; adding it to unrestricted UserInput would unnecessarily expand staff-input surfaces.
- A genuine authenticated non-staff customer can edit their own birthday; a genuine authenticated superuser can edit customer birthdays. Deny guests, other customers, ordinary staff (including staff editing self), apps with `MANAGE_USERS`, and `IMPERSONATE_USER` apps. A superuser is not an eligibility exemption.
- Add birthday to account/customer update tracking. Authorization happens when the field is present, including explicit null; ordinary name-only edits must stay valid. Detailed spec must settle explicit-null transport semantics without treating omission as clearing.
- Birthday resolver is nullable and returns the date only to the same customer or superuser; unauthorized selection returns no birthday value. Keep ordinary Dashboard fragments birthday-free. Exclude it from customer/order payloads, exports, search, metadata, logs, analytics and shared caches. Subscription selections must pass the same resolver guard.

### Eligibility and decision inputs (R4–R6)

- Proposed module: `saleor/saleor/core/age_restrictions.py` (new; small shared domain helper, no GraphQL dependency). Inputs: current durable policy snapshot, customer birthday, shop-local date, restriction-bearing products and operation context.
- Calculate the threshold anniversary by adding the minimum age to the birthday year; replace 29 February with 1 March when the target year is non-leap. Eligible iff shop-local today is on/after that anniversary. Never divide elapsed days, use UTC today, trust browser date/time zone, or convert birthday to a timestamp.
- Determine shop-local `today` once per decision from an aware clock converted using the durable, validated `timeZone`. Compare birthday/threshold/today as date values only; equality qualifies. Use writer-side current settings/customer/product state at protected decisions, not token claims, client flags, cached eligibility or a cart-time snapshot. Time-zone calculation remains backend-only; Paper does not select or display the field. Trace: R2/R4 → B8/B9/B21–B26.
- Restricted checkout add/increase needs an authenticated customer identity. For guests, **all non-removal quantity updates to a restricted line are blocked**, not just increases; lower or unchanged positive quantities are still updates. Removal, including quantity zero resolved as removal, remains allowed without an age-policy rejection. Existing restricted lines stay in place until explicitly removed; browsing is not gated. A signed-in customer may act on their still-anonymous cart before attach (P8); a cart belonging to another customer is not a source of usable birthday authority. Staff/apps are not blanket bypasses: evaluate the actual linked customer for their legitimate delegated operations.
- A guest-supplied email, including one later matched to an account (B23), never substitutes for sign-in on a restricted shopper checkout. Automatic completion evaluates durable checkout customer identity, not just optional task requestor; app order conversion evaluates the linked customer. Neither is exempt.
- Missing birthday and underage are ineligible. Return a privacy-safe domain rejection containing offending product/variant/line identity, not birthday, exact customer age or the matched account's existence. API adapters map it to their error enums and existing error fields.
- Completion message names the product, e.g. “Cannot complete checkout: Sample Product is age-restricted.” Use a safe catalog label; no birthday/reason details from another user's record. Define stable additive error codes consistently across CheckoutErrorCode, OrderErrorCode and OrderCreateFromCheckoutErrorCode; reorder's separate error contract also needs explicit mapping.

**Consistency boundary:** Reuse existing aggregate locks and writer rules; refetch policy inputs at final decision rather than reusing request-dataloader/legacy pre-payment snapshots. Define the decision snapshot/lock order in the detailed spec and test concurrent quantity/policy/profile changes. Do not hold new global policy locks across payment-provider calls. No legal identity-verification claim is made: birthday is self-declared under the approved requirement.

### Clients and compatibility (R9–R10)

- **Dashboard product:** ProductDetailsForm + create/edit form types/defaults/mappers/submit composition and product fragment. Boolean must travel through changed-field payloads using presence tests; disable/read-only according to existing product permissions. No per-product numeric input.
- **Dashboard settings:** SiteSettingsPage includes minimum age and the new IANA `timeZone` field with UTC default, inline server validation and current saved values. Wire `Shop.timeZone` through `src/fragments/shop.ts` and `src/siteSettings/queries.ts`; submit `ShopSettingsInput.timeZone` through the page form/view mapping and `src/siteSettings/mutations.ts`. This zone UI exists in Dashboard Site Settings only, not Paper. Use existing macaw/react-intl settings components. Trace: R2 → D5/D6/D8.
- **Dashboard customers:** Do not expose birthday to ordinary staff. Superuser API access is provided; a new superuser-specific Dashboard birthday editor is not requested and is not required for the two mandated Dashboard screens. Customer details/forms/fragments are regression/privacy boundaries.
- **Paper profile:** Add a date-input editor using account settings/actions and self-only CurrentUserProfile selection. Keep canonical `YYYY-MM-DD` strings end to end; backend validates. Do not put birthday in broad public product/cart projections or customer order queries.
- **Paper notice/sign-in:** Product flag travels via ProductDetails and ProductView mapper into notice props. Fetch session/public minimum-age policy, **excluding `timeZone`**, through loaders inside dynamic Suspense islands; never personalize a cached product shell. Guest browsing remains available; restricted product/cart/checkout surfaces prompt sign-in with locale/channel-safe links. Authenticated customer gets profile guidance as needed. Shared templates/UI remain transport-free. Trace: R5/R9 → P6–P8.
- **Paper carts:** Add restriction flag to CheckoutFind/checkout line projections and plain cart view model. Keep retained guest restricted lines visible; disable non-removal quantity updates/increases and prompt sign-in, but keep explicit removal enabled. Return/render structured add/update errors without changing the retained cart on rejection; do not emit add-to-cart success analytics on a rejected mutation. Signed-in decrease recovery follows the delta policy, not the stricter guest-update rule. No `timeZone` selection/display. Trace: R5/R8 → P4/P5/P13.
- **Paper checkout:** Retained guest restricted lines block completion; show sign-in prompt and the backend's authoritative product-named error through the existing fieldErrors/result contract. Restriction notice and sign-in/profile recovery belong in contact/payment flow, without `timeZone` selection/display. Do not conflate unavailable session with guest. Preserve authorized-payment recovery and free-order completion; a rejected completion never offers another charge as the remedy. Trace: R6 → B22–B26/P9.
- **Schema rollout:** Backend first (fields/defaults/migrations/schema), then refreshed Dashboard pins/codegen and both Paper codegen sets. Backend schema command: `uv run poe build-schema`; Dashboard: schema refresh under later resource approval, then `pnpm run generate`; Paper: `pnpm run generate:all`. Do not hand-edit generated code.
- **Older clients:** Optional inputs keep unrestricted catalog/account/checkouts compatible; new restricted purchases intentionally fail until profile/sign-in support exists. Unknown new enum values need generic safe-error fallbacks, not exhaustive unchecked mappings. New clients querying an old API fail GraphQL validation: require a matching API version/schema; never silently treat unavailable fields as “unrestricted.”
- **Dashboard dual schemas:** Refresh both pins to supported backend contracts or use established schema locks and UI gating for fields genuinely absent in one supported pin. Build-time schema locks are not runtime discovery of an arbitrary older API. Do not add unlocked selections/unsupported input values to one schema while claiming both are compatible.
- **Paper boundaries:** New operation registry entries use session auth only where required; public minimum-age policy can be live/read-only, with no `timeZone` selection. Preserve data/core locks and contract version rules. Existing generated directories are ignored, and checkout generation requires an API; generation is not permissible in this discovery session.

## Risks, reversibility and remaining design review

- **Policy scope:** Endpoint-only checks and model hooks both miss or misclassify meaningful operations; preserve the protected-operation inventory as a regression matrix.
- **Identity:** Email auto-association is not authentication. Do not use another account's birthday just because a guest supplies its email or knows a checkout identifier.
- **Privacy:** Shared User type, app impersonation, inherited inputs and tracked saves are the highest-risk seams. A broadly permitted birthday field is not acceptable.
- **Current-state races:** Legacy processing unlocks before payment; final recheck can reject after authorization/charge. Preserve existing failure handling, fund state and recovery; no claims of atomicity across payment providers.
- **Data freshness:** Product notices can be cached, but purchase enforcement cannot. Shop setting changes currently lack an automatic non-metadata revalidation event; use live policy reads rather than assuming storefront cache invalidation.
- **Regulatory limit:** Self-declared birthday implements the approved feature, not identity verification, regional alcohol/tobacco law compliance or legal consent/retention policy.
- **Compatibility:** New optional fields are additive; changed restricted-purchase behavior is intentional. Schema mismatches and new error enums still require coordinated releases/fallback tests.
- **Reversibility:** Keep additive columns during application rollback. Rollback to old code removes enforcement and therefore is not a safe policy rollback once restricted sales are enabled; pause restricted sales rather than silently running old policy-free code. No destructive rollback is proposed.
- **Approval gate:** Parent presents this draft for explicit design approval before detailed specs/plan; later spec/test review gates cover precise names, integer/null semantics, error mappings, snapshot/lock order and recovery UX. These are proposed technical contracts, not assumed existing behavior.

**Assumptions:** None adopted. The design-review confirmations above explicitly fix `timeZone`, its Dashboard-only UI scope, and retained guest-line/update/removal/completion behavior. Remaining proposed API/database names, helper location, scoring weights and adapter layout await review; they are not facts or implicit approvals. No runtime compatibility, query counts, performance or test success is assumed.

**Deviations:** Initial discovery halted because `python` was unavailable; caller explicitly approved resumption with `python3`/read-only tools. Some guessed source paths were absent and were subsequently resolved from directory/source evidence. One read-only filename listing inadvertently used `sort`/`tail` beyond the resumed command allowlist; no prohibited data was read and no resource/write resulted. No state/memory/documentation updates were made, honoring the single-file write scope over workflow bookkeeping. No nested agents or dynamic workflows were launched.

**Work not performed:** No application implementation, schema/codegen generation, migration/test creation or execution, database/service/network/cloud access, environment/key/log/seed/customer-data reads, commits or pushes. Only this architecture note was authored. Original end-to-end definition of done remains outstanding.

This is an architectural assessment, not measured runtime assurance.
